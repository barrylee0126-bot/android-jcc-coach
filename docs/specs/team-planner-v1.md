# 真人教练阵容候选规划 v1

代码入口：[jcc_team_planner](../../src/jcc_team_planner/)。它是为“玩家自己操作、系统给提示”准备的纯输入候选计算器：在同一明确版本、模式和规则修订下，根据调用方已确认的棋盘、备战席、商店、人口、金币、棋子羁绊及门槛，枚举至多三种可上场组合。

每种组合会列出：上场实例、至多一张当前商店购买、购买后的金币、已激活羁绊档位及相对当前棋盘的羁绊变化、保留的核心实例、上场/下场变化。排序只优先展示**更多已声明羁绊档位**、更少换人和更低购买开销的组合；它不是单位强度、装备效果、对局胜率或“最优阵容”的评分。

## 输入与未知边界

`plan()` 只接受显式 JSON 数据：

- `binding`：`game`、`region`、`mode`、`season`、`patch` 和 `rules_revision`，不能是 `unknown/current/latest`；
- `unit_catalog`：唯一棋子 ID、价格、羁绊和调用方声明的职责标签；
- `trait_catalog`：每个羁绊的严格递增门槛；
- `trait_counting_rule` 与 `merge_rule`：两者都要和局面版本绑定完全一致。前者须明确同名实例是否分别计羁绊；后者须明确一星合二星数量和购入后是否自动合星；
- `board` 与 `bench`：每一枚棋子须有唯一 `instance_id`、明确星级、核心标志和已穿装备 ID；同一实例不能同时出现；另需明确 `bench_capacity`。完整组合搜索有 5,000 个组合预算；超出预算时，结果保留当前阵容基线，并只比较「当前棋盘 + 一名备战棋子或一张当前商店购买」形成的一次上人或一次换人，明确标为 `single_swap_local_only`。`lineup_search.search_scope` 写明实际范围，`scope_exhaustive` 只表示这个已声明范围已枚举完成，绝不表示全局策略穷尽；
- `shop`：至多五个明确格子，价格须与同一棋子目录一致；
- `level_capacity`、金币与准备阶段。

任何字段缺失、版本不明确、同一实例重复、同名计数规则不明、当前快照需要合星、棋盘或备战席超容量、核心棋子无法同时保留、商店价格冲突或非准备阶段都会返回 `unknown`，不会把它解释成空棋盘、空商店或零金币。备战席满、金币不足或购买会触发未建模合星时，会明确排除该购买。模块不会读取屏幕、平板、视频或账号；调用方的 `verified` 声明仍只是声明。

星级和同名棋子实例会原样保留；只有版本绑定的计数规则明确允许时，v1 才按每个被上场的**已知实例**计入羁绊。它不会把三张同名一星自动合成二星，也不猜测棋子是否唯一、是否应追三或商店刷新概率。

## 羁绊、装备与转型

羁绊按棋子目录中明确的羁绊 ID 计数，输出当前数量、最高激活门槛和下一门槛。它不把羁绊数量等同真实战力，也不根据单位名字推断适用阵容。

可选 `transition_targets` 允许调用方声明转型目标的必要棋子与羁绊档位。输出只显示已经持有、当前商店正好可见和仍缺失的棋子；当所有缺失棋子都在当前商店时才计算其总价，否则成本为 `null`，不编造刷新次数或转型可达性。即便该价格为 `0`，它也只表示没有已知缺失棋子；人口、核心保留、目标羁绊是否达到、装备承接和即时战力会分别输出，绝不等价于“零成本完成转型”。

可选 `equipment` 复用已发布的 [jcc_recipe_candidate](recipe-candidate-v1.md) 来计算调用方完整闲置散件库存中**各自**可合成的配方。它要求配方请求和阵容请求的版本绑定完全一致，且由调用方给出每件成品的可携带实例；输出按每个阵容候选列出适配、且未满三件装备的上场实例，不比较装备效果、不会判断最佳携带者。多个配方可能争用同一散件，不能同时合成的情况保持未知。若某个可合成成品缺少携带者规则，则不会把它当作“没有适配者”：`equipment_evaluation` 为 `partial_unknown`，并在 `equipment_unknown_item_ids` 逐件列出；有规则但所有声明携带者已满三件时，才是该已知规则下的空候选。未提供 `equipment` 时 `equipment_candidates` 为 `null`、`equipment_evaluation` 为 `not_requested`，与已评估但没有适配结果的空列表不同。

本项目 S18 数据入口是[版本数据 README](../../资料/版本数据/README.md)。其中第三方英雄、羁绊和装备数据以及当前补丁均未实机验证，且存在[待核查冲突](../../资料/版本数据/待核查_数据冲突.json)。因此仓库不自动加载这些数据给规划器，也不能把本模块的合成示例解释为当前国服建议。

## 运行与验证

全部测试使用虚构棋子、羁绊、价格、装备散件和版本；不加载真实游戏资料：

```sh
PYTHONPATH=src PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B \
  -m unittest discover -s src/jcc_team_planner/tests -v

# 查看纯虚构、版本绑定的输入和输出
PYTHONPATH=src PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B \
  -m jcc_team_planner --demo
```

测试覆盖：羁绊档位变化、单张可负担商店购买、核心保留（含备战席核心）、备战席容量、同名计数和合星阻断、转型缺口和不完整成本、严格版本/人口/实例/商店校验、配方模块复用及逐件装备未知、重复 JSON 键与输入不变性。候选固定保留当前阵容基线，并显示任何替换所移除的星级和已穿装备数；显示的备选按羁绊档位覆盖、变动数和购买成本排序，只有前三条，附总枚举数、截断标志和计算预算。通过只说明明确输入的候选计算；不证明视觉识别、版本适配、装备效果、实战策略或上分效果。
